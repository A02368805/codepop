# FloatStack Test Design Report

## Testing Philosophy

**Pragmatic, friction-driven testing:** AI can easily cover unit tests, so we use it for all of them. We write integration tests reactively when UAT reveals friction. We focus on manual testing for user-facing workflows.

**Our approach:**
1. **Unit tests** — AI generates these automatically for models, services, and utility functions. They're straightforward (clear inputs/outputs, no side effects), so we accept high-quality AI output.
2. **Integration tests** — We write these reactively. When UAT uncovers a friction point (e.g., cart checkout behaves strangely, sync fails under race conditions), we create an integration test to lock down that behavior and prevent regression.
3. **UAT (User Acceptance Testing)** — We manually test against actual user stories. This is where we catch layout bugs, permission gaps, and workflow issues no unit test would reveal.

**Why this works:** Unit tests are deterministic and easy to auto-generate—might as well have AI do it. Integration tests are where we invest engineering judgment—they target real pain points discovered during testing, not hypothetical edge cases. UAT keeps us honest about whether the system actually works for users.

---

## How We Test

We use **pytest** (with **pytest-django**) for automated testing and **coverage.py** to measure code coverage. Automated tests catch logic bugs (orders, payments, permissions, models). Manual testing catches things automated tests miss (layout, formatting, edge cases, real-world workflows). Frontend testing relies on browser-based UAT and HTMX-targeted integration tests since our architecture avoids complex JavaScript.

---

## Test Layers

### Unit Tests
- **What:** Models, services, selectors, utility functions in isolation
- **Tools:** pytest + pytest-django
- **Run:** `make test` (runs all tests) or `make test path/to/test_file.py` for specific files
- **Coverage:** Generated by `make coverage`
- **AI-friendly:** These are straightforward to auto-generate because they have clear inputs/outputs and no side effects

### Integration Tests  
- **What:** Multi-component workflows (order placement with payment, inventory updates with sync, manager actions with permission checks)
- **Tools:** pytest + pytest-django with database transactions; HTMX responses tested via Django test client
- **When:** Created reactively when UAT reveals bugs or friction points
- **Example:** Cart checkout test that verifies order creation, payment intent, inventory deduction, and sync message all work together
- **Coverage:** Tracked alongside unit tests in overall `make coverage` output

### End-to-End / Manual Testing (UAT)
- **What:** Real browser, real workflows, user stories from requirements document
- **Tools:** Browser + manual interaction (no automation framework; human testers run each scenario)
- **Focus:** Layout, permissions, multi-step workflows, edge cases (CSV encodings, concurrent edits)
- **Mapped to:** Specific user stories (Story 62, Story 40, etc.) for traceability

### Frontend Testing (HTMX & Browser)
- **What:** HTMX response structure tested via Django test client (unit/integration); layout/interaction tested manually in browser
- **Note:** No separate E2E framework (Selenium, Cypress) needed. Our server-rendered + HTMX architecture means:
  - HTMX swaps HTML snippets (testable as HTTP responses)
  - Layout issues must be caught by human eyes in browser
  - Form interactions tested both via test client (does HTMX return right HTML?) and manually (does it render/respond correctly on mobile?)

## CI/CD & Automation

Tests run automatically on every commit:
- **Local:** `make test` runs tests in Docker; `make coverage` generates coverage report locally (Python 3.12, PostgreSQL 16)
- **Remote (GitHub Actions):** 
  - Runs on every push to `dev` or `master` branches and on pull requests
  - **Lint job:** Black and isort checks (must pass)
  - **Test job:** `make ci-test` runs full test suite with PostgreSQL (must pass)
  - Tests run outside Docker on Python 3.12 with a PostgreSQL 16 service container
- **Coverage reporting:** Coverage is generated locally and reviewed before PR merge (no automated gate in CI yet)
- **Manual gate:** UAT results required before release (story-by-story pass/fail documented)

## What We're Worried About

**Mobile layout.** Tests verify we send the right HTML, but don't catch if buttons are misaligned or form inputs are broken on small screens.

**CSV parsing.** We test clean UTF-8 files. Weird encodings, Windows line breaks, or embedded quotes might break the parser.

**Multi-store sync.** We fake network calls in tests. Real delays and out-of-order changes might cause issues.

**Concurrent edits.** If two managers edit the same inventory item at the exact same time, one might lose their change.

**Background tasks.** Tests run them instantly; production runs them separately. We don't know if that causes timing bugs.

## Code Coverage

**Overall: 78%** of code is tested by automated tests (unit + integration combined).

**By layer:**
- **Models (95%+):** Rock solid. Inventory, orders, payments, stores, sync, supply hubs—the critical data structures. Unit tests verify field validation, defaults, and relationships.
- **Services & selectors (85-90%):** Business logic is solid. Order services (placement, refunds), sync services, permission selectors all heavily tested with both unit and integration tests.
- **Views (39-92% depending on app):** Weaker coverage. Store views & forms (33-44%), location views—this is where integration tests catch missing pieces. Order views (60%), payment views (62%). REST endpoints generally better-tested than web template views. *This is where manual UAT will find bugs.*
- **AI assistant code (orders/assistant.py) (21%):** Specialized, hard to unit-test in isolation. Requires manual verification during UAT and focused integration tests for real prompt/response scenarios.

**What coverage means:**
- Unit test coverage on models/services = high confidence in isolated logic
- View coverage = checks that templates render and HTMX endpoints return correct HTML, but doesn't verify layout or browser interaction
- Missing coverage = untested code paths; likely source of bugs found during UAT

Run `make coverage` anytime to see the full breakdown. Coverage metrics are tracked in CI/CD and reported on PRs.

## Manual Testing Plan (UAT)

Instead of generic test scenarios, we're testing the actual user stories from our requirements document. Each story represents a real user workflow, and we'll verify each one works end-to-end. **When UAT uncovers friction or bugs, we create integration tests to lock down the behavior and prevent regression.**

For example:
- UAT finds: "Cart checkout is slow on mobile"  
  → Integration test: Add test covering cart → payment intent → order creation with timing assertions
- UAT finds: "CSV import fails with Windows line breaks"  
  → Integration test: Add test case with `\r\n` line endings to CSV parser
- UAT finds: "Manager can edit same inventory as another manager at same time and one edit is lost"  
  → Integration test: Concurrent PATCH requests to same inventory item; verify last-write-wins or conflict handling

### Guest/General User Stories

**Story 62**: As a general_user, I want to place orders without creating an account so that I can try the service without a registration barrier.
- Steps: Navigate to home, find a store, customize a drink, check out with test card, verify order is created.
- Verify: Can place order without login. Payment completes. Order code is unique and findable.

**Story 59**: As a general_user, I want to select a store location manually so that I can order from a specific location without enabling geolocation.
- Steps: Go to stores, manually enter a location or click a store from the list (without geolocation permission), customize, checkout.
- Verify: Store selection works without geolocation. Form accepts manual location. Checkout completes.

**Story 63 & 65**: As a general_user, I want to customize drinks using available ingredients and see all available options.
- Steps: Browse menu, verify all syrups/sodas/ice cream show up, click each option to customize, add to cart.
- Verify: All ingredients display correctly. Customization options work. Cart reflects selections.

**Story 67**: As a general_user, I want a full refund if I cancel my order before preparation begins.
- Steps: Place order, immediately go back, cancel before it moves to "preparing," verify refund message shows.
- Verify: Refund is processed immediately. Order status updates to canceled.

### Cross-Role Permission Tests

Test that unauthorized roles cannot access restricted pages:
- Customer trying to access `/manager/` → 403 or redirect
- Manager trying to access `/logistics/` → 403 or redirect
- Repair staff trying to access `/orders/` → 403 or redirect
- Logistics person trying to access another region's stores → not in filters

Verify data filtering works:
- Each manager only sees their store
- Each logistics person only sees their region
- Each customer only sees their own orders and favorites

## What Will Probably Break

Mobile layout issues. HTMX updates not showing up. CSV files with weird encodings. Missing permission checks on a few pages. Sync not waking up to send changes.

---

## Summary

**Testing strategy:** AI generates unit tests → we write integration tests reactively based on UAT friction → we manually test all user stories end-to-end.

We're testing against 20+ actual user stories from our requirements document. Each story is a real workflow that a user expects to work. If a story passes, the system works for that use case. If it fails, we:
1. Fix the bug
2. Write an integration test to prevent regression  
3. Document the issue and resolution
4. Re-run UAT to confirm the fix

**After testing, we'll report:**
- Which stories passed / failed / required fixes
- Integration tests written in response to UAT friction  
- Remaining known gaps (mobile layout, concurrency, CSV edge cases) and whether they're acceptable tradeoffs or blockers
